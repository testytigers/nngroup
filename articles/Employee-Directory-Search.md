<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>Guidelines conflict on whether to limit intranet search to a single search box or dedicate an additional box to employee directory searches.  There&#x27;s theory to support both guidelines. What&#x27;s up?

</div>

<div class="article-body">

<p>In recent studies on how <a class="old" href="http://www.nngroup.com/reports/intranet-usability-guidelines/" title="Nielsen Norman Group report: Intranet Usability: 111 Design Guidelines from Studies with Intranet Users"> employees in a range of companies use their intranets</a>, an important guideline emerged: intranets should provide a <strong> dedicated search box </strong> for finding phone numbers and other <strong> employee directory information</strong>. Preferably, this staff directory box should appear on every page of the intranet, and it should definitely appear on the top levels of an enterprise portal and on the main intranet homepage.</p>

<p><em>That's one usability guideline. </em></p>

<p>At the same time, one of the most established <a class="old" href="/articles/search-visible-and-simple/" title="Alertbox May 2001: Search: Visible and Simple"> usability guidelines for search</a> is to provide no more than a <strong> single search box </strong> on the homepage. Competing homepage search boxes are confusing, and advanced search should be relegated to a secondary position inside the site to avoid seducing users away from the simple search, which they're more likely to use correctly.</p>

<p><em>That's another, <strong> conflicting</strong>, usability guideline. </em></p>

<p>And a conflict it is. Our own usability testing of intranets, for example, revealed serious problems when intranets had multiple searches: users often used the wrong search without knowing it. To the users' mind, <strong> search is search</strong>, and if they type something into a query field and hit return, they expect to find what they're looking for. They often don't realize that the same action can have different outcomes depending on subtle details, such as the difference between two search mechanisms. We thus have two guidelines:</p>

<ul>

<li><strong>Two search boxes</strong>. The first is for full-text queries, and the second for searching the employee directory</li>

<li><strong>One search box</strong>. One, I say. What part of "one" don't you understand?</li>

</ul>

</div><h2 id="toc-considering-basic-hci-principles-1">Considering Basic HCI Principles</h2>

<p>When in trouble, appeal to a higher authority. In usability, this authority is provided by the basic principles for human-computer interaction -- fundamental insights that have proven sound over more than twenty years of studies and research.</p>

<p>Unfortunately, both search box guidelines are supported by basic principles.</p>

<p>The two-search guideline is supported by the principle of providing <strong> accelerators for frequent actions</strong>. We know from our research that looking up colleagues in the employee directory is one of the key intranet killer apps in many companies. This action is performed so frequently that a shortcut seems in order.</p>

<p>The one-search guideline is supported by two strong principles: simplicity and consistency. <strong> Simplicity </strong> says that fewer commands mean less potential for users to mess up and choose the wrong one. That's why the Macintosh mouse has only one button. <a class="old" href="http://www.nngroup.com/books/coordinating-user-interfaces-for-consistency/" title="Book: 'Coordinating User Interfaces for Consistency'"> <strong> Consistency</strong></a> says that the same action should have the same result, and yet typing text into a search box and hitting return would have different outcomes depending on which box was used in the two-search design.</p>

<h2 id="toc-resolution-examine-the-user-experience-2">Resolution: Examine the User Experience</h2>

<p>It is very common to have conflicting usability guidelines. They are called "guidelines" rather than "specifications" for a reason: they are necessarily fuzzy because they relate to human behavior.</p>

<p>Interface design requires <strong> trade-offs</strong>. The challenge is in knowing how to balance the conflicting guidelines and in understanding what is most important in a given situation.</p>

<p>In the employee directory question, there are two arguments for why <strong> the new two-search guideline is correct</strong>: empirical evidence and theoretical reasoning.</p>

<p>When in doubt, you can always <strong> run a user test</strong>. We've tested many intranets with separate employee directory boxes, and uniformly found that this design worked well.</p>

<p>It's nice to have empirical validation for a user interface, but ultimately it's not very satisfying if you cannot explain <em> why </em> something works. Granted, you may have resolved one issue, but your skill at analyzing future design dilemmas remains unchanged.</p>

<p>So: what is the theory that explains why employee directory search works?</p>

<p>The consistency counter-argument is a canard. Searching an employee directory is not truly a "search" in the human way of thinking. As users see it, <strong> search is when you type in a word and find documents </strong> that contain that word. In using the employee directory box, you type in a name, not a word. And you find a person, not a document. Because these actions are very different, there is no expectation that the two boxes should behave the same.</p>

<p>Of course, any programmer reading this will protest, "but a name <em> is </em> a word" and "finding records for people in the database <em> is </em> a query for a set of objects that's no different from document retrieval." Correct on both counts: Deep in the guts of the machine, searching the employee directory and searching a document repository are indeed very similar, though the database implementations might differ. <strong> What matters, though, is not the implementation, but the user experience. </strong> And, to the user, there is a world of difference between people and documents. The two are not equivalent classes of "objects." People are your colleagues -- live human beings. Anyone can tell the difference between Joe in Accounting and an accounting memo.</p>

<p>There is something to the simplicity counter-argument: an extra box does take up <a class="old" href="/articles/homepage-real-estate-allocation/" title="Alertbox Feb. 2003: Homepage Real Estate Allocation"> pixels, which are in short supply on a homepage</a>. But simplicity's most important aspect does not work against employee search. Users don't have to spend time worrying about which query mechanism to use for different searches, for the simple reason that they don't think of employee search as a search. (Which is why you should label this feature something other than "Search," such as "Find Employee.")</p>

<h2 id="toc-clarity-is-the-key-3">Clarity Is the Key</h2>

<p>As we have seen in testing intranets, using one search to find documents from the document repository and another search to find answers in the knowledge base is a big problem for users. Most people won't know which is which, and they'll waste much time trying to puzzle out the difference. But, when you want to find Mary's phone number, you don't think of it as a document retrieval operation. You think of it as looking up Mary in the employee list. For both needs, the action to take is clear, so users have only one command to consider in each case. Exactly the outcome the simplicity principle aims to achieve.</p>

<p>The basic human-computer interaction principles sound obvious and reasonable, but as this example shows, their interpretation requires subtlety. The usability field is one in which <strong> empirical observation and theoretical analysis reinforce each other</strong>. Because the theory is so weak, analyses get better as you continue to supplement theory with empirical experience. And, when you know the principles and guidelines, your empirical observations get richer because you know what to look for.</p>
