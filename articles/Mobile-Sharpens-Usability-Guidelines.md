<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>Many guidelines are similar for mobile and desktop design, but their mobile interpretation is much more unforgiving.

</div>

<div class="article-body">

<p>My recent column <a class="old" href="/articles/condense-mobile-content/" title="Alertbox"> Mobile Content: If in Doubt, Leave It Out</a> advised site owners to eliminate secondary material when writing for mobile users. Many tweets, blog postings, and other comments on the article all expanded on this theme: <em> Yes, do cut the fluff from mobile content, but <strong> also cut secondary content when writing for desktop websites. </strong> </em></p>

<p>In one way, I can only agree. Since 1997, <a class="old" href="/articles/how-users-read-on-the-web/" title="Alertbox: How Users Read on the Web"> conciseness has been a key guideline</a> when writing for the web. People <a class="old" href="/articles/how-little-do-users-read/" title="Alertbox: How Little Do Users Read?"> don't read a lot on the web</a> and <a class="old" href="/articles/how-long-do-users-stay-on-web-pages" title="Alertbox: How Long Do Users Stay on Web Pages?"> leave in a few seconds</a> if a site doesn't communicate its value clearly. These findings lead to more detailed guidelines, such as <a class="old" href="/articles/first-2-words-a-signal-for-scanning/" title="Alertbox: First 2 Words: A Signal for the Scanning Eye"> emphasizing the first 2 words</a> of nanocontent (e.g., headlines and search engine links).</p>

<p>So yes, <a class="old" href="/articles/blah-blah-text-keep-cut-or-kill/" title="Alertbox: Blah-Blah Text: Keep, Cut, or Kill?"> cut the blah-blah</a> from your desktop site.</p>

</div><h2 id="toc-mobile-is-less-forgiving-than-desktop-1">Mobile Is Less Forgiving than Desktop</h2>

<p>However, there's still a difference between writing for the web and writing for mobile:</p>

<ul>

<li>Desktop copywriting must be concise.</li>

<li>Mobile copywriting must be <em> even more </em> concise.</li>

</ul>

<p>The high-level guideline is the same: reduce secondary info. The <strong> difference is one of degree </strong> — certain information that might be acceptable on a desktop site <strong> should be removed from </strong> a mobile site or app.</p>

<p>Our original <a class="old" href="/articles/defer-secondary-content-for-mobile/" title="Alertbox: Defer Secondary Content When Writing for Mobile Users"> research on how people read on mobile devices</a> used the example of sending users a coupon with a special offer. In the study, the best design presented fairly limited information on the first screen. To read "more about this deal" users had to tap a link.</p>

<p>In a desktop design, it would have been better to show all the information on the first screen and save users a click. Why this difference?</p>

<ul>

<li>Mobile <strong> screens are much smaller</strong>: reading through a peephole increases cognitive load and makes it about <a class="old" href="/articles/mobile-content-is-twice-as-difficult/" title="Alertbox: Mobile Content Is Twice as Difficult"> twice as hard to understand text</a> on a mobile device as on a desktop. <a class="old" href="/articles/short-term-memory-and-web-usability/" title="Alertbox: Short-Term Memory and Web Usability"> Short-term memory is weak</a>, so the more users have to remember after it scrolls off the screen the worse they'll do.</li>

<li>Mobile users are <strong> even more rushed </strong> than desktop users because of the mobile setting.</li>

</ul>

<p>Both differences support the same recommendation: <strong> be more severe </strong> when cutting text for mobile than for desktop.</p>

<p>A similar finding applies to the choice of functionality: the <a class="old" href="/articles/mobile-usability-update/" title="Alertbox: Mobile Usability Update"> feature set should be much smaller</a> for a mobile site than for a desktop site. For sure, desktop sites should offer <strong> as few features as possible</strong>. For every feature that's removed, the UI has one less thing to confuse users and thus makes the remaining features easier to use.</p>

<p>But a mobile site should have <strong> even fewer features </strong> than the desktop site. (Thus the guideline to offer a link from the mobile site to the full site for users who need features that only the desktop site supplies.) The mobile site should have only those features that make sense for the mobile use case. For example, a company's full site typically includes <a class="old" href="/articles/press-area-usability/" title="Alertbox: Press Area Usability"> PR information</a> and <a class="old" href="/articles/investor-relations-ir/" title="Alertbox: Investor Relations (IR) on Corporate Websites"> investor relations sections</a>, but this info should be eliminated from the mobile site.</p>

<p>Your desktop <a class="new" href="http://www.nngroup.com/topic/information-architecture/" title="Nielsen Norman Group 2-day training course: Information Architecture - Structuring and Organizing Web-Based Information"> information architecture (IA)</a> should always feature a simple navigation space that avoids an overly deep hierarchy. But for mobile, the limited space makes it even more important to prevent user disorientation; you should thus limit the navigation options, because you can't show full contextual information on every screen. (The total screen space allocated to navigation on a typical desktop site is <em> more </em> than the entire screen of a typical smartphone, leaving no room for the content.) That is, your navigation <a href="/articles/flat-vs-deep-hierarchy/">structure should be even shallower</a> in a mobile IA.</p>

<p><strong>Tablets form an intermediate case </strong> somewhere between phones and desktops. Tablets' mid-sized screens allow for more context in both writing and navigation than what fits on mobile screens and also supports richer features. On the other hand, the larger space encourages more complex gestures, which leads to its own usability problems, as discovered in our <a class="old" href="/reports/ipad-app-and-website-usability/" title="Nielsen Norman Group reports: Usability of iPad Apps and Websites"> research with iPad users</a>.</p>

<h2 id="toc-usability-guidelines-are-rarely-dichotomies-2">Usability Guidelines Are Rarely Dichotomies</h2>

<p>People want me to give hard and fast rules: don't show more than <em> X </em> menu items; don't write more than <em> Y </em> words per page; nothing should be more than <em> Z </em> clicks from the homepage. Sadly, UI design doesn't work that way. Usability questions seldom have a single answer. Rather, they are qualitative issues that <a class="old" href="/articles/interaction-elasticity/" title="Alertbox: Interaction Elasticity"> specify the direction and nature of inevitable design tradeoffs</a>.</p>

<p>Every time your web page's <a class="old" href="/articles/website-response-times/" title="Alertbox: Website Response Times"> response time</a> increases by 0.1 seconds, you'll lose a few percent of your visitors. But it's not true that <em> everybody </em> will wait 10 seconds while <em> nobody </em> will wait 11 seconds.</p>

<p>As another example, take the guideline about concise writing. The most concise copy would be a word or two, but that would typically make for an unsatisfactory web page. In fact, <a class="old" href="/articles/content-strategy-long-vs-short/" title="Alertbox: Long vs. Short Articles as Content Strategy"> sometimes longer articles can be better</a> (though even in-depth articles should cut the fluff and be written at an appropriate <a class="old" href="/articles/cloze-test-reading-comprehension/" title="Sidebar: Alertbox: Cloze Test for Reading Comprehension"> comprehension level</a> for their target audience).</p>

<p>The simple point remains: it's best to squeeze the text when writing for the web (as well as follow the many other <a class="old" href="/topic/writing-web/" title="Jakob Nielsen: list of articles about writing for the web"> web content guidelines</a>). If writing for mobile, simply squeeze that orange even more. When considering which secondary content to defer to secondary pages, you need to move the cut-off point between primary and secondary when targeting mobile users. The principle remains the same, but your judgment should be harsher for mobile.</p>

<p>In all areas of user experience — feature set, IA, writing, images, and more — mobile usability requires stricter and more scaled-back design than desktop usability. That's why you need a <strong> separate mobile design</strong>. Simply using responsive web design to make the full site accessible on mobile devices results in a substandard mobile UX. (This is actually an old lesson repeated for a new medium: <a class="old" href="/articles/accessibility-is-not-enough/" title="Alertbox: Accessibility Is Not Enough"> accessibility ≠ usability</a>.)</p>
