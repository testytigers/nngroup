<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>Users overlook features if the GUI elements (such as buttons and checkboxes) are too far away from the objects they act on.

</div>

<div class="article-body">

<p>One of the oldest principles of human-computer interaction is that things that are <strong> close together on the screen are seen as related</strong>. (Similarly, users view as related those things that are the same <strong> color </strong> or <strong> shape</strong>, that <strong> move </strong> or <strong> change </strong> together, or that reside within an <strong> enclosure</strong>, such as a box.)</p>

<p>I wrote about how to apply the <strong>proximity gestalt principle </strong> to GUI design in my 1993 book <a class="old" href="http://www.nngroup.com/books/usability-engineering/" title="Book by Jakob Nielsen"> <cite> Usability Engineering</cite></a>, but it was well documented long before that.</p>

<p>Even though it's an ancient insight and is covered in countless books and courses, we frequently see <a class="old" href="/articles/tunnel-vision-and-selective-attention/" title="Alertbox: Tunnel Vision and Selective Attention"> <strong> users overlook features </strong> because layouts violate the proximity rule</a>. When buttons, drop-downs, checkboxes, or other actionable GUI elements are too far away from the objects they act on, people don't see them. Often, users don't realize what they're missing and simply assume the features aren't available.</p>

<p>In <a class="new" href="/reports/ecommerce-user-experience/" title="Nielsen Norman Group report: E-Commerce User Experience Guidelines"> e-commerce studies</a>, for example, users often overlook the availability of products in additional colors or sizes.</p>

</div><h2 id="toc-itunes-violation-of-the-proximity-guideline-1">iTunes' Violation of the Proximity Guideline</h2>

<p>A striking example here comes from the screen in Apple's iTunes software for upgrading iPhone applications to newer releases. Several months after getting an iPhone, I still thought users had to manually check each application icon one at a time.</p>

<p>This is how it looks:</p>

<p style="text-align:center"><a class="new" href="http://media.nngroup.com/media/editor/2013/03/14/itunes-distant-button_fullsize.png" title="Click for full size of this screenshot"><img alt="Screenshot showing huge distance between a group of icons and a button that acts on them" border="0" height="547" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/itunes-button-distance-small.png" width="800"/> </a></p>

<p>At the top of the screen are a bunch of application icons. At the very bottom of the screen is a button labeled <em> 1 Update Available</em>. When clicked, this button updates whatever app needs the update, sidestepping the need for users to click each icon.</p>

<p>But, for several months, I <strong> didn't notice this button </strong> because the action is simply too far removed from the objects it applies to.</p>

<p>Furthermore, the button lives in a separate colored stripe, so it appears to be outside the space that the icons inhabit, violating a key <a class="old" href="/courses/topic/visual-design/" title=" Nielsen Norman Group: detailed description of training course"> visual interface design principle</a>.</p>

<p>(As an aside, why is the iTunes window so large in my screenshot, when it contains only a few icons? Because the same application manages both the phone's apps and its music collection. When you work with several hundred sound tracks, you need a <em> big </em> space. It's not always good to try to support highly distinct tasks within a single GUI.)</p>

<h2 id="toc-close-vs-far-buttons-2">Close vs. Far Buttons</h2>

<p>Interestingly, iTunes presents an example of correct button placement in another part of the same workflow:</p>

<p style="text-align:center"><img alt="Dialog area with 2 buttons" height="132" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/buttons-1-near-1-far-small.png" width="800"/></p>

<p>In this screenshot, the <em> Get Update </em> button is right next to the icon it acts on. No risk of overlooking this feature. And no questions about what you can do. (Sadly, the dialog area's <em> Done </em> button might as well be in Siberia. In fact, one problem is that this screen uses dialog areas for the role of dialog boxes in an interaction.)</p>

<p>That mainstream corporate websites make blatant usability mistakes is understandable because most members of their teams aren't grounded in graduate degrees in human-computer interaction. (That's why we have added foundational courses, such as <a class="new" href="https://www.nngroup.com/courses/human-mind/" title="Nielsen Norman Group: detailed outline for training tutorial"> The Human Mind</a>, to the UX Conference.) But how could <em> Apple</em>, of all companies, make such an elementary GUI design mistake? Apple has been pretty good at graphical user interfaces since it <a class="old" href="/articles/macintosh-25-years/" title="Alertbox: Macintosh 25 Years"> brought them to the mass market in 1984</a>.</p>

<p>First, this is simply one more example proving that the <strong> big boys make mistakes </strong> and that you shouldn't copy everything you see in best-selling software or popular websites. (This was brought home clearly in recent studies for our "<a class="new" href="/articles/copying-a-famous-sites-design/" title="Alertbox: Should You Copy a Famous Site's Design?">Big and Famous Sites</a>" project where apple.com was one of the sites we tested. But that's a story for another day.)</p>

<p>Second, the usability problem might not have seemed so bad in Apple's own testing:</p>

<ul>

<li>If the tests used a <strong> smaller window</strong>, the button would have been closer to the icons and less likely to be overlooked by test users. (A smaller window might have resulted from using a normal-sized monitor or from testing the features in isolation so users wouldn't be interacting with the large workspace needed to accommodate an entire music collection.)</li>

<li>If they tested a configuration with <strong> more app icons</strong>, the icons would have filled up the space and thus the button would have been closer to the last icon.</li>

</ul>

<p>This case exemplifies the continued importance of an old and tried GUI guideline: insights that were <a class="old" href="/articles/durability-of-usability-guidelines/" title="Alertbox: Durability of Usability Guidelines"> discovered decades ago</a> will still bite you if you forget them. The misplaced iTunes button also shows the importance of including a range of <strong> realistic configurations and sample data</strong>, both during user testing and in design reviews.</p>
