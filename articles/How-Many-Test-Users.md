<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>The answer is 5, except when it&#x27;s not. Most arguments for using more test participants are wrong, but some tests should be bigger and some smaller.

</div>

<div class="article-body">

<p>If you want a single number, the answer is simple: <strong><a class="old" href="/articles/why-you-only-need-to-test-with-5-users/" title="Alertbox: Why You Only Need to Test with 5 Users"> test 5 users in a qualitative usability study</a>.</strong> Testing with 5 people lets you find almost as many usability problems as you'd find using many more test participants.</p>

<p>This answer has been the same since I started promoting "<a class="old" href="/articles/discount-usability-20-years/" title="Alertbox: Discount Usability 20 Years">discount usability engineering</a>" in 1989. Doesn't matter whether you test websites, intranets, PC applications, or mobile apps. With <strong>5 users</strong>, you almost always get close to user testing's maximum benefit-cost ratio.</p>

</div><h2 id="toc-exceptions-to-the-rule-1">Exceptions to the Rule</h2>

<p>As with any human factors issue, however, there are <strong> exceptions</strong>:</p>

<ul>

<li><a class="old" href="/articles/quantitative-studies-how-many-users/" title="Alertbox: Quantitative Studies: How Many Users to Test?">Quantitative studies</a> (aiming at statistics, not insights): Test at least <strong>20</strong> users to get statistically significant numbers; tight confidence intervals require even more users.</li>

<li><a class="old" href="/articles/card-sorting-how-many-users-to-test/" title="Alertbox: Card Sorting: How Many Users to Test">Card sorting</a>: Test at least <strong>15</strong> users per user group.</li>

<li><a class="old" href="/reports/how-to-conduct-eyetracking-studies/" title="Free Nielsen Norman Group report: Eyetracking Methodology - Guidelines for How to Conduct and Evaluate Usability Studies Using Eyetracking">Eyetracking</a>: Test <strong>39</strong> users if you want stable heatmaps.</li>

</ul>

<p>However, these exceptions shouldn't worry you much: the vast <a class="old" href="/articles/accuracy-vs-insights-quantitative-ux/" title="Alertbox: Accuracy vs. Insights in Quantitative Usability"> majority of your user research should be qualitative</a> — that is, aimed at collecting <strong> insights to drive your design</strong>, not numbers to impress people in PowerPoint.</p>

<h2 id="toc-return-on-investment-2">Return on Investment</h2>

<p>The main argument for small tests is simply <strong> return on investment</strong>: testing costs increase with each additional study participant, yet the number of findings quickly reaches the point of diminishing returns. There's little additional benefit to running more than 5 people through the same study; ROI drops like a stone with a bigger <em> N</em>.</p>

<p>And if you have a big budget? Yay! Spend it on additional studies, not more users in each study.</p>

<p>Sadly, most companies insist on running bigger tests. During the <a class="new" href="https://www.nngroup.com/ux-conference/" title="Conference program and list of usability training tutorials">UX Conference</a>, I surveyed 217 participants about the practices at their companies. The average response was that they used <strong> 11 test participants </strong> per round of user testing — more than twice the recommended size. Clearly, I need to better explain the benefits of small-<em>N </em> usability testing.</p>

<h2 id="toc-weak-arguments-for-more-test-participants-3">(Weak) Arguments for More Test Participants</h2>

<blockquote>

<p><strong>"A big website has millions of users." </strong></p>

</blockquote>

<p>Doesn't matter for the sample size, even if you were doing statistics. An opinion poll needs the same number of respondents to find out who will be elected mayor of Pittsburgh or president of France. The variance in statistical sampling is determined by the sample size, not the size of the full population from which the sample was drawn. In user testing, we focus on a website's functionality to see which design elements are easy or difficult to use. The evaluation of a design element's quality is independent of how many people use it. (Conversely, the decision about whether to fix a design flaw should certainly consider how much use it'll get: it might not be worth the effort to improve a feature that has few users; better to spend the effort recoding something with millions of users.)</p>

<blockquote>

<p><strong>"A big website has hundreds of features." </strong></p>

</blockquote>

<p>This is an argument for running several <em> different tests </em> — each focusing on a smaller set of features — not for having more users in each test. You can't ask any individual to test more than a handful of tasks before the poor user is tired out. Yes, you'll need more users overall for a feature-rich design, but you need to spread these users across many studies, each focusing on a subset of your research agenda.</p>

<blockquote>

<p><strong>"We have several different target audiences." </strong></p>

</blockquote>

<p>This can actually be a legitimate reason for testing a larger user set because you'll need representatives of each target group. However, this argument holds only if the different users are actually going to behave in completely different ways. Some examples from our projects include</p>

<ul>

<li>a medical site targeting both doctors and patients, and</li>

<li>an auction site where you can either sell stuff or buy stuff.</li>

</ul>

<p>When the users and their tasks are this different, you're essentially running a new test for each target audience, and you'll need close to 5 users per group. Typically, you can get away with 3–4 users per group because the user experience will overlap somewhat between the two groups. With, say, a financial site that targets novice, intermediate, and experienced investors, you might test 3 of each, for a total of 9 users — you won't need 15 users total to assess the site's usability.</p>

<blockquote>

<p><strong>"The site makes so much money that even the smallest usability problem is unacceptable." </strong></p>

</blockquote>

<p>Rich companies certainly have an <a class="old" href="/articles/when-high-cost-usability-makes-sense/" title="Alertbox: High-Cost Usability Sometimes Makes Sense"> ROI case to spend more on usability</a>. Even if they spend "too much" on each quality improvement, they'll make even more back because of the vast amounts of money flowing through the user interface. However, even the highest-value design projects will still optimize their ROI by keeping each study small and conducting many more studies than a lower-value project could afford.</p>

<p>The basic point is that it's okay to leave usability problems behind in any one version of the design as long as you're employing an <a class="old" href="/articles/parallel-and-iterative-design/" title="Alertbox: Parallel &amp; Iterative Design + Competitive Testing = High Usability "> iterative design process</a> where you'll design and test additional versions. Anything not fixed now will be fixed next time. If you have many things to fix, simply plan for a lot of iterations. The end result will be higher quality (and thus higher business value) due to the additional iterations than from testing more users each time.</p>

<h2 id="toc-83-case-studies-4">83 Case Studies</h2>

<p>The following chart summarizes 83 of Nielsen Norman Group's recent <a class="new" href="https://www.nngroup.com/consulting/" title="Nielsen Norman Group: usability consulting servcies"> usability consulting projects</a>. Each dot is one usability study and shows how many users we tested and how many usability findings we reported to the client. (The chart includes only normal qualitative studies; we also run competitive studies and benchmark measurements, and conduct other types of research not shown here.)</p>

<div style="text-align:center">

<figure class="caption" style="display:inline-block"><img alt="Scatterplot of 83 usability-testing case studies, showing the number of users tested in each study as well as the number of usability findings reported." height="448" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/usability-problems-by-users-tested.png" width="651"/>

<figcaption>There's a small correlation, but it's really tiny. Across these many projects, testing more users didn't result in appreciably more insights.</figcaption>

</figure>

</div>

<p>Why did we run more users in the first place, given that I certainly believe my own research results showing the superiority of small-<em>N </em> testing? Three reasons:</p>

<ul>

<li>Some clients wanted bigger studies for internal credibility. When a study's sponsor presents findings to executives who don't understand usability, the recommendations are easier to swallow when more users were tested. (If management trusted its own employees, much money could be saved.)</li>

<li>Some design projects had multiple target audiences and the differences in expected (or at least <em> suspected)</em> behaviors were large enough to justify the expense of sampling additional users.</li>

<li>Finally, the very fact that these were consulting projects justified including a few more users, which is why we often run studies with around 8 users. ROI is the ratio between benefits and expense. When hiring a consultant, the true expense is higher than just the fee because the client must also spend time finding the consultant and negotiating the project. With higher investment, you want a larger benefit.</li>

</ul>

<p>The last point also explains why the true answer to "how many users" can sometimes be much smaller than 5. If you have an <a class="old" href="/articles/agile-user-experience-projects/" title="Alertbox: Agile User Experience Projects"> Agile-style UX process</a> with very low overhead, your investment in each study is so trivial that the cost–benefit ratio is optimized by a smaller benefit. (It might seem counterintuitive to get more return on investment by benefiting less from each study, but this savings occurs because the smaller overhead per study lets you run so many more studies that the sum of numerous small benefits becomes a big number.)</p>

<p>For really <strong>low-overhead projects</strong>, it's often optimal to test as few as <strong>2 users per study</strong>. For some other projects, 8 users — or sometimes even more — might be better. For most projects, however, you should stay with the tried-and-true: 5 users per usability test.</p>
