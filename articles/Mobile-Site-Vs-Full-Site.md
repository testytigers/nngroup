<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>Good mobile user experience requires a different design than what&#x27;s needed to satisfy desktop users. Two designs, two sites, and cross-linking to make it all work.

</div>

<div class="article-body">

<p>Based on <a class="old" href="/articles/mobile-usability-update/" title="Alertbox: Mobile Usability Update"> usability testing of hundreds of sites</a>, the main guidelines for mobile-optimized websites are clear:</p>

<ul>

<li><strong>Build a separate mobile-optimized design </strong>(or <em> mobile site</em>) if you can afford it. When people access sites using mobile devices, their measured usability is much higher for mobile sites than for full sites.

<ul>

<li>A mobile <a class="old" href="/articles/mobile-sites-vs-apps-strategy-shift/" title="Alertbox: Mobile Sites vs. Apps: The Coming Strategy Shift"> app might be even better</a>— at least for now.</li>

</ul>

</li>

<li>If mobile users arrive at your full site,<strong> automatically show them the mobile version.</strong> Sadly, many search engines still don't rank mobile sites high enough for mobile users, so people are often (mis)guided to full sites instead of the mobile ones, which offer a vastly superior user experience.</li>

<li>Offer a clear <strong> link from your full site to your mobile site </strong> for users who end up at the full site despite the redirect.</li>

<li>Offer a clear <strong> link from your mobile site to your full site </strong> for those (few) users who need special features that are found only on the full site.</li>

</ul>

<p>We've tested hundreds of mobile sites and full sites on all the currently popular platforms (including iPhone, Android, Windows Phone, and BlackBerry). The findings regarding mobile and full sites were the <strong> same for all the different phones</strong>, so I won't discuss specific devices here.</p>

<p>The <a class="old" href="/articles/ipad-usability-year-one/" title="Alertbox: iPad Usability, Year One"> guidelines are different for large tablets</a> (10-inch form factor, as in Apple iPad, Lenovo IdeaPad, Samsung Galaxy, etc.), where full sites work reasonably well. For small tablets (7-inch form factor, as in <a class="old" href="/articles/kindle-fire-usability-findings/" title="Alertbox: Kindle Fire Usability Findings"> Amazon Kindle Fire</a>) the ideal would be to create yet a third design optimized for mid-sized devices, though most companies can get away with serving their mobile site to Kindle Fire users.</p>

</div><h2 id="toc-mobile-optimized-sites-1">Mobile-Optimized Sites</h2>

<p>The <a class="new" href="http://www.nngroup.com/reports/mobile-website-and-application-usability/" title="Nielsen Norman Group report: Usability of Mobile Websites and Apps - 237 Design Guidelines for Improving Access to Web-Based Content and Services Through Mobile Devices"> complete design guidelines for mobile websites</a> require almost 300 pages, so I can't cover everything here. The basic ideas are to:</p>

<ul>

<li><strong>cut features</strong>, to eliminate things that are not core to the mobile use case;</li>

<li><strong>cut content</strong>, to reduce word count and <a class="old" href="/articles/defer-secondary-content-for-mobile/" title="Alertbox: Defer Secondary Content When Writing for Mobile Users"> defer secondary information</a> to secondary pages; and</li>

<li><strong>enlarge interface elements</strong>, to accommodate the "fat finger" problem.</li>

</ul>

<p>The challenge is to eliminate features and word count without limiting the selection of products. A mobile site should have less information about each product and fewer things users can do with the products, but the range of items should remain the same as on the full site. If users can't find a product on a mobile site, they assume the company doesn't sell it and go elsewhere.</p>

<p>So, for example, a mobile real estate site should show all the homes for sale in a neighborhood, not just the ones most people are interested in buying. (Though it could offer a shortlist of popular houses as a shortcut so users could view them with a single touch.) But the mobile site could eliminate esoteric features — such as a property's past sales history — and offer users who need these features a link to the info on the full desktop site.</p>

<h2 id="toc-why-full-sites-dont-work-for-mobile-use-2">Why Full Sites Don't Work for Mobile Use</h2>

<p>It's common today to hear people argue the following: <strong> Mobile users have increasingly high expectations </strong> for what they should be able to accomplish on their phones, so eliminating content or features will inevitably disappoint some people. It's therefore better, the (flawed) argument goes, to serve the full site to everybody, including mobile users.</p>

<p>This analysis is flawed because it assumes that the only choice is between the full-featured desktop site and a less-featured mobile site. However, any mobile site that complies with the usability guidelines will provide links to the full site wherever features or content are missing, so users have access to everything when and if they need it.</p>

<p>The design challenge is to place the cut between mobile and full-site features in such a way that the <strong> mobile site satisfies almost all the mobile users' needs</strong>. If this goal is achieved, the extra interaction cost of following the link to the full site will be incurred fairly rarely.</p>

<p>True, we've seen some underpowered and poorly designed mobile sites that would hardly satisfy anybody's mobile needs. But bad design that misinterprets a guideline is no reason to throw the baby out with the bathwater and neglect the well-documented guideline itself. (In fact, if miserable user interfaces were a reason to reject an entire design category, we wouldn't have the Web at all; there are plenty of virtually unusable websites around. But that doesn't mean that we can't design good sites by following the guidelines that bad sites violate.)</p>

<p>The correct analysis goes as follows:</p>

<ul>

<li>For the vast <strong> majority of tasks</strong>, mobile users will get a <strong> vastly better user experience </strong> from a well-designed mobile site than from the full site.</li>

<li>For a small <strong> minority of tasks</strong>, mobile users will be <strong> slightly delayed </strong> by the extra click to the full site.</li>

</ul>

<p>A big gain that's experienced often will comfortably outweigh a small penalty that's suffered rarely.</p>

<p>A second argument against the mobile site option is that you could <strong> just optimize the entire website for mobile </strong> in the first place. Then, giving mobile users the "full" site wouldn't cause them any trouble. While true, this analysis neglects the <strong> penalty imposed on desktop users </strong> when you give them a design that's suboptimal for bigger screens and better input devices (see sidebar on <a class="new" href="/articles/mouse-vs-fingers-as-input-device/" title="Alertbox sidebar: Mouse vs. Fingers as Input Device"> mouse vs. fingers</a>). If desktop users were a minute minority this might be acceptable, but almost all websites get substantially more traffic (and even more business) from desktop users than from mobile users. So, while we do want to serve mobile users, we <a class="old" href="/articles/transmedia-design-for-3-screens/" title="Alertbox: Transmedia Design for the 3 Screens (Make That 5)"> can't neglect desktop users</a>— who, after all, pay most of our salaries.</p>

<p>The basic point? The <strong> desktop user interface platform differs from the mobile user interface platform </strong> in many ways, including interaction techniques, how people read, context of use, and the plain number of things that can be grasped at a glance. This <strong> inequality is symmetric</strong>: mobile users need a different design than desktop users. But, just as much, desktop users need a different design than mobile users.</p>
