<span class="article-summary-label">

Summary:&nbsp;

</span>Interaction techniques that deviate from common GUI standards can create usability catastrophes that make applications impossible to use.

</div>

<div class="article-body">

<p>I can operate almost any user interface. After all, I have <a class="old" href="/articles/30-years-with-computers" title="Alertbox: Thirty Years With Computers"> 33 years' experience using computers </a> and 25 years' professional experience analyzing bad designs: I know most of the ways interaction designers can confuse or annoy users. I've seen it all before. Or so I thought.</p>

<p>Despite my prowess at defeating complicated user interfaces, I was recently stumped by a simple dialog box. I simply couldn't figure out how to proceed, so I had to close the application and use another program to achieve my goal.</p>

<p>The offending software shall remain nameless; it's a nice piece of shareware that I enjoy enough to have paid the fee. Also, a single developer serves as both the programmer and interface designer on the application, so it would be unfair to pick on him.</p>

</div><h2 id="toc-wheres-the-ok-button-1">Where's the <em> OK </em> Button?</h2>

<p>The usability problem appeared after I upgraded to the application's newest release and wanted to save a file in a new image format. As the following screenshots show, this brought up the expected "Save As" dialog box, along with a smaller, overlaid dialog box containing a property sheet with the image format's special options.</p>

<p> </p>

<p style="text-align: center"><a href="http://media.nngroup.com/media/editor/2013/03/14/dialog-box-no-ok.png"><img alt="Screenshot of two dialog boxes from a graphics application: a 'Save As' dialog and a property sheet" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/dialog-box-no-ok-67pct.png" style="border: 0px; width: 655px; height: 316px;"/> </a><br/>

<em>The dialog boxes that appeared when saving a file. </em></p>

<p>The options window should have included a <em> Help </em> feature, because many of its options were rather obscure. As is typical of users who don't understand their options, I <a class="old" href="/articles/the-power-of-defaults" title="Alertbox: The Power of Defaults"> left the settings at the default values </a> , particularly since I was satisfied with the defaults for those settings that I did understand. This is as it should be: if you <strong> pick good defaults </strong> , most users can ignore any advanced options and simply proceed.</p>

<p>My obvious next step was to accept the default options by <strong> clicking the <em> OK </em> button </strong> to dismiss the options box. Surprise: there was no such button!</p>

<p>However hard I tried, I couldn't get the application to show me an <em> OK </em> button. I tried saving in another format. I tried rebooting first the app, and then the entire computer. Nothing worked.</p>

<p>It was impossible for me to get rid of the active dialog box and get back to my "Save As" dialog box. I gave up. Defeated by a dialog box.</p>

<h2 id="toc-what-youre-supposed-to-do-2">What You're Supposed to Do</h2>

<p>A week later, I tried the software again. This time, for some reason, I clicked the Save button in the main dialog box without messing with the options. Surprise again: this worked, and my file was saved.</p>

<p> </p>

<p>Turns out that <em> you don't have to accept the option settings </em> . The software will apply whatever settings are active in the options window when you click <em> Save </em> in the "Save As" dialog box.</p>

<p>This completely non-standard GUI behavior caused a <strong> catastrophic failure in usability </strong> : the user (me) completely abandoned the application.</p>

<p>Having the user give up represents a usability problem of the highest severity level. It's only because I had positive experiences with several previous releases that I gave this app one more chance. If I'd been trying this piece of software for the first time, there wouldn't have been a second time.</p>

<p>Upon further experimentation, I discovered another way of getting rid of the options box: uncheck the checkbox marked "Show options dialog." This, of course, completely violates the <a class="old" href="/articles/checkboxes-vs-radio-buttons" title="Alertbox: Checkboxes vs. Radio Buttons"> design rules for checkboxes and radio buttons </a> , which are not supposed to have any immediate effect when they are clicked. Only after the user clicks <em> OK </em> should the system take action on any checkbox selections.</p>

<h2 id="toc-respect-the-user-illusion-3">Respect the User Illusion</h2>

<p>Once you know how to operate this user interface, it's easy enough to use. But of course, users don't magically understand special interaction techniques, whether they appear in a software upgrade or a new application. <strong> Most users know only the standard interaction techniques </strong> that all of their other applications use.</p>

<p>Users understand standard GUI rules such as:</p>

<ul>

<li>One window at a time is active, and that's the one you interact with, because that's the one that has input focus.</li>

<li>The latest window to open is the active one; when one window spawns a sub-window, you have to deal with it first.</li>

<li>You can change the input focus to another window by clicking within it. (I didn't try this because I "knew" it would be necessary to specify the options first.)</li>

<li>Dialog boxes are dismissed by clicking <em> OK </em> or <em> Cancel </em> .</li>

</ul>

<p>There are many more rules as well, and all of them have remained the same since 1984, when the original specifications for the modern GUI were published in <cite> Inside Macintosh </cite> .</p>

<p>When you comply with these standard rules, users can <strong> focus on your application's meaning </strong> , rather than the physical operation of the mouse. There is enough complexity in the app's feature set; don't add to users' confusion by making them solve problems before they can click a button or type data into a text field. Figuring out which button to click and what data to type is hard enough.</p>

<p>One of the modern GUI's greatest advances is the <strong> user illusion </strong> that the mouse pointer is an extension of your hand: <strong> you own the pointer </strong> , which has a certain physicality to it as you use it to manipulate objects on the screen. Of course, all of this is only an illusion, because the mouse pointer is really under software control. Clicking the physical mouse while the on-screen pointer rests on a picture of something isn't <em> really </em> the same as clicking an object.</p>

<p>However, you must retain the user illusion of direct manipulation at all cost, because that's what makes users <strong> feel in charge of their computers </strong> .</p>

<p>Because there's no true physicality, the <strong> user illusion is maintained by complying with the low-level rules for GUI object behavior </strong> . Even the smallest deviation bursts the bubble and reveals the fact that users aren't really controlling their destinies.</p>

<p>It's very disconcerting when the laws of nature stop working. It blows away all that you thought you knew, and leaves you feeling weak and threatened.</p>

<p>Obeying design conventions and standards is the way to retain and strengthen <a class="old" href="/articles/ideologies-of-web-design" title="Mastery, Mystery, and Misery: The Ideologies of Web Design"> users' feelings of mastery over technology </a> .</p>

<h2 id="toc-solutions-4">Solutions</h2>

<p>Fixing this usability problem is easy enough. There are four main possibilities, all of which operate within the standard GUI interaction rules:</p>

<ul>

<li>Retain the current <strong> two-window design </strong> , but add <em> OK </em> and <em> Cancel </em> buttons to the options dialog. (Although you should usually <a class="old" href="/articles/reset-and-cancel-buttons/" title="Alertbox: Reset and Cancel Buttons"> avoid <em> Cancel </em> and <em> Reset </em> buttons on websites </a> , applications need <em> Cancel </em> because users sometimes experiment with alternate options, so they need a way to back out and retain the standard settings.)</li>

<li>Eliminate the separate options box and <strong> show the options within the main "Save As" window </strong> using <a class="old" href="/articles/progressive-disclosure" title="Alertbox: Progressive Disclosure"> progressive disclosure </a> : make options visible only when the user clicks a button to change options.</li>

<li>Have users proceed through a <strong> sequence of dialog boxes </strong> , so that only one box is visible at any given time. Photoshop uses this approach: first you go through "Save As" and specify where the application should save the file, and which format it should use. You then get a separate dialog box to specify the chosen image format's settings.</li>

<li>Make the image format options into a <strong> preference setting </strong> that users must specify in advance, before they issue the <em> Save </em> command. This is dangerous if the options are important, because many users will overlook the need to go through a special step before issuing a command. But for obscure options that most people will never need, the preference route works well because it's less likely to distract or confuse novice users.</li>

</ul>

<p>To summarize the four designs, the options can be presented <strong> next to </strong> the main window, <strong> within </strong> this window, <strong> after </strong> the main command, or <strong> before </strong> it.</p>

<p> </p>

<p>The one-dialog design is my preferred solution, because it's the simplest for the common scenario in which users don't want to change the options. Photoshop's two-step design might be better if there are many options or if you need sub-dialogs to specify particularly advanced settings.</p>

<h2 id="toc-the-key-lesson-consistency-5">The Key Lesson: Consistency</h2>

<p>The lesson from this case study is not how to design a better "Save As" dialog. Depending on the circumstances, you could use any of the four designs I listed, or perhaps even design a fifth that works better for your particular type of data. It's easy enough to find out what's best for your users and their tasks: mock up the leading contenders as <a class="old" href="http://www.nngroup.com/reports/prototyping/" title=" Nielsen Norman Group: training video on paper prototyping"> paper prototypes </a> , and test them with a handful of users.</p>

<p> </p>

<p>The big lesson here is the need to <strong> stick with the design conventions that users know </strong> . Whatever design you pick should work in the expected manner.</p>

<p>Don't redesign the meaning of the vocabulary you employ to communicate with users. You can put words together in new ways, as long as you keep using words from the standard language. Just because a GUI uses a visual language of buttons, windows, and the like doesn't change the fact that <strong> it's a language </strong> . Changing the interaction design primitives has the same effect as writing in Greek to an English-speaking audience.</p>
