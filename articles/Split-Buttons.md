<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>A split button is a dual-function menu button that offers a default action as well as the possibility of choosing a different action by selecting from a set of alternatives.

</div>

<div class="article-body">

<p>In complex applications, it is easy to overwhelm users with a tremendous number of options, commands, tools, and controls. Showing a large number of tools all at once is visually overwhelming, and evaluating all the available actions places far too much <a href="https://www.nngroup.com/articles/minimize-cognitive-load/">cognitive load</a> on users. Split buttons reduce visual complexity by grouping similar commands together — much like how navigation menus chunk together related options to enable conceptual understanding of the site information structure.</p>

<p style="margin-left:40px"><strong>Definition</strong>: A split button is a button with two components: a label and an arrow; clicking on the label selects a default action, and clicking on the arrow opens up a list of other possible actions.</p>

<p>A split button is a hybrid between a button and a menu: it groups related commands together into a <a href="https://www.nngroup.com/articles/drop-down-menus/">dropdown</a>, but also offers one-click access to a default choice that doesn’t require opening the menu.</p>

<figure class="caption"><img alt="A menu button on the left with the word Paragraph that has no default choice.  A split button with the word Insert on the right that has a default choice.  Both menus are open." height="564" loading="lazy" src="https://media.nngroup.com/media/editor/2019/04/25/menu-and-split-buttons.png" width="788"/>

<figcaption><em><strong>Left</strong>: The </em>Paragraph<em> button is a regular menu button. Clicking anywhere on the button opens the menu, and there is no default choice made by clicking </em>Paragraph<em>.<br/>

<strong>Right</strong>: The </em>Insert<em> button is a split button. Clicking </em>Insert<em> itself performs the default action of inserting text but does not open the menu, whereas clicking the arrow part of the button opens a menu, providing several related commands.</em></figcaption>

</figure>

<p>Split buttons are for presenting several related tools if one option is used most frequently. Making the most commonly accessed option a <a href="https://www.nngroup.com/articles/the-power-of-defaults/">default</a> lowers the <a href="https://www.nngroup.com/articles/interaction-cost-definition/">interaction cost</a> to use that option since it removes the need to open the menu before selecting the item. The obvious penalty is that accessing the menu becomes harder because it requires hitting a small target (which takes <a href="https://www.nngroup.com/videos/fittss-law/">more time according to Fitts’s Law</a>) and also involves an extra mental operation to decide which part of the button to activate.</p>

<p> Unlike <a href="https://www.nngroup.com/articles/contextual-menus/">contextual menus</a>, split buttons are typically placed in a main toolbar, and the commands found within their associated menu are not limited to options related to items the user has already selected before triggering the menu.</p>

<p>While a split button may seem like an obvious design pattern, options within the menu can have low <a href="https://www.nngroup.com/articles/navigation-ia-tests/">discoverability</a>. Users (especially those learning an application) don’t always recognize this pattern, so they may not notice the secondary menu button and, consequently, the options located within the menu. Therefore, the first thing to consider when deciding whether to use split buttons is whether there is a strong choice for the default option; if users only notice the default option, will that serve the majority of situations? If not, a traditional menu button (without a default option) may assist users better by promoting discovery, especially in an application that doesn’t see a lot of repeat usage.</p>

<p>In desktop applications, menu buttons are used for commands and tools rather than for navigation. Thus, the second aspect to consider when using a split button is whether that button will be hosting commands versus navigation categories (in fact, we recommend that you <a href="https://www.nngroup.com/articles/split-buttons-navigation/">don’t use split buttons for website navigation</a>): if the result of clicking the button is an <em>action</em> or <em>selecting a tool</em> then a split button is appropriate, whereas if the button takes a user to <em>another page</em> <em>or screen</em>, a <a href="https://www.nngroup.com/articles/drop-down-menus/">standard dropdown menu</a> is a better choice than a split button.</p>

</div><h2 id="toc-visually-separate-arrow-button-1">Visually Separate Arrow Button</h2>

<p>Good visual design is essential for a split button to be recognized: <strong>the arrow that signals the menu aspect of the button must be clearly separated from the label of the button</strong>.</p>

<p>A poorly designed split-button can look like a standard menu button (which always opens the menu). Strong visual <a href="https://jnd.org/signifiers_not_affordances/">signifiers </a>for split buttons include a dividing line within the button or a slightly different color for the region around the arrow. The visual separation between the default action and the arrow should be always visible, and not simply a hover effect — when the visual separation between is hidden until hover, users will not properly recognize a split button.</p>

<figure class="caption"><img alt="A split button that has no clear visual separation between the arrow and the default button parts. " height="174" loading="lazy" src="https://media.nngroup.com/media/editor/2019/04/25/hidden-signifier.png" width="831"/>

<figcaption><em>Menu button or split button? The arrow button is not visually separated from the default </em>Paste<em> action (left) until the user hovers over that region of the button (right). This hidden signifier is not as effective as one that is always shown.</em></figcaption>

</figure>

<p>The target size of the arrow component of the split button is a major limiting factor on its usability. If the size of the arrow button is very small (as it often happens), that button will be harder to acquire (according to Fitts’s Law). As a result, we do not recommend split buttons for touchscreen applications (because of the <a href="https://www.nngroup.com/articles/mouse-vs-fingers-input-device/">fat-finger problem</a>), unless it is possible to make tap target sizes for <em>both</em> parts of the button at least <a href="https://www.nngroup.com/touch-targets">1cm × 1cm</a>.</p>

<p>Adobe Photoshop, for example, attempts to circumvent this sizing issue and places the arrow ambiguously within the bottom right corner of each split button, allowing (and requiring) a click-and-hold gesture <em>anywhere</em> on the button to open the menu. This solution is not recommended, as there is no visual signifier for that unique affordance; we have observed that even veteran users of Photoshop do not realize that they can click and hold anywhere on the button to access its menu component; instead, they would attempt to position their mouse cursor over the tiny arrow icon. And some of those who painstakingly succeed are disappointed to discover that the menu does not open on click (requiring instead a click and hold).</p>

<figure class="caption"><img alt="Photoshop's use of split buttons that has a very small arrow in the bottom right corner of the button" height="249" loading="lazy" src="https://media.nngroup.com/media/editor/2019/04/25/photoshop-ambiguous-split-button.png" width="252"/>

<figcaption><em>Photoshop uses split buttons for the main toolbar, but does not clearly signify that the menu should be opened by clicking and holding anywhere on the visible target area. This design causes learnability problems for new Photoshop users, who often attempt to hone their mouse cursor over the tiny arrow icon and click to open the menu.</em></figcaption>

</figure>

<h2 id="toc-use-text-labels-for-split-buttons-2">Use Text Labels for Split Buttons</h2>

<p>Some split buttons have both an icon and text in the label component. While icons are optional, <a href="https://www.nngroup.com/videos/icon-text-labels/">a text label is always necessary</a>. Text improves learnability, discoverability, and findability, and increases the target size of the button, thus providing a Fitts’s Law benefit. The default choice in a split button should always include a text label, and so should the alternate options inside the menu.</p>

<p>Unlike regular menu buttons, in which the text label should clearly describe a generic <em>category</em> comprising all that is contained in the menu, a split button’s visible text label should be a <a href="https://www.nngroup.com/articles/ui-copy/">descriptive name of the <em>default tool </em>or command</a>.</p>

<figure class="caption"><img alt="Row height button with a categorical label, because it is a menu button.  The reply button, on the right, is a split button, and the text label is a verb." height="402" loading="lazy" src="https://media.nngroup.com/media/editor/2019/04/25/splitbuttoncategory.png" width="545"/>

<figcaption><em><strong>Left</strong>: The </em>Row Height <em>button is a regular menu button, and the text label is a category description for the options in the menu.<br/>

<strong>Right</strong>: The </em>Reply<em> button is a split button, and the text label is the name of the default action, rather than a description of the entire category.</em></figcaption>

</figure>

<h2 id="toc-other-tips-for-effective-split-buttons-3">Other Tips for Effective Split Buttons</h2>

<p>While many of these recommendations carry over from other types of menus such as <a href="https://www.nngroup.com/articles/contextual-menus/">contextual menus</a> and <a href="https://www.nngroup.com/articles/menu-design/">menu bars</a>, abiding by these rules ensures that split buttons work well:</p>

<ul>

<li><strong>Limit the overall number of choices </strong>within the menu to less than 10–12, to avoid <a href="https://www.nngroup.com/articles/simplicity-vs-choice/">choice paralysis </a>and the tedious need to review a long list of items to find the desired one.</li>

<li><strong>Avoid submenus within split buttons</strong>, as it is difficult to move the cursor to the submenu without accidentally closing the main menu.</li>

<li><strong>Disable items that are not relevant</strong> or unavailable for the current task.</li>

<li><strong>Order the items within the menu</strong> <strong>by popularity</strong> (for a small number of items), <strong>or alphabetically</strong> (for a larger number of items with names that will be known to users). Ordering helps users find the command they need without having to exhaustively review all options. For a small number of items (fewer than 5 or so), ordering them by popularity makes the most important items quickly available. For more than 5 menu options, alphabetical order makes it easier for users to predict where to find a known item in the menu order (according to <a href="https://www.nngroup.com/videos/hicks-law-long-menus/">Hick-Hyman law</a>).</li>

<li><strong>If keyboard shortcuts are available for any options within the menu, make those visible next to the command</strong> to promote learnability.</li>

</ul>

<h2 id="toc-persistent-split-buttons-4">Persistent Split Buttons</h2>

<p>A useful variation of split buttons is called a <strong>persistent split button</strong> (sometimes known as a <strong><a href="https://www.nngroup.com/articles/modes/">modal </a>split button</strong>). In this type of button, the default changes to the last action selected by the user (from the list of actions in the split-button menu). Thus, the user’s menu choice persists as the default (until, of course, the user makes a different selection from the menu). Thus, persistent split buttons allow a degree of <a href="https://www.nngroup.com/videos/personalization-customization/">customization </a>for each user without the necessity of going through preferences and advanced application settings (<a href="https://www.nngroup.com/articles/customization-of-uis-and-products/">which many users will not engage with</a>). They also speed up repetitive work or work in batches, where a user might utilize one option from a split button repeatedly for a short while, then switch to a related tool for a while, and so on.</p>

<p> </p>

<figure class="caption"><img alt="A persistent split button, where the user's selection becomes the new default." height="222" loading="lazy" src="https://media.nngroup.com/media/editor/2019/04/25/persistent-split-button.png" width="412"/>

<figcaption><em>In the Windows Snipping Tool application, choosing an option from the split button’s menu (such as </em>Window Snip<em>) becomes the new default option, and clicking </em>New<em> would thereafter trigger a </em>Window Snip<em> (until the user chooses a different option from the menu). It is worth noting that in this example, the default label button remains, </em>New<em>, rather than </em>Window Snip<em>, which is very likely to cause confusion if the user is not aware of the current default state.</em></figcaption>

</figure>

<p>However, the benefit that persistent split buttons have for power users has a <a href="https://www.nngroup.com/articles/novice-vs-expert-users/">similarly strong detriment to new users</a>. As users learn an interface, they rely on familiar cues, such as the position of a command within the interface, in order to recall where that command is. This spatial consistency helps to build a mental model of the UI. As the interface changes (for example because labels for buttons change), even subtly, with each use, the context clues to build that mental model become weaker, and the UI is less easy to learn. Users might be forced to ask themselves “where was that button again?” while trying to find a useful tool.</p>

<p>That is why persistent buttons are best avoided when you have a mix of power users and occasional users.</p>

<h2 id="toc-summary-5">Summary</h2>

<p>Split buttons are most useful in repeat-use desktop applications with a large number of commands that need to be consolidated. While split buttons are efficient for accessing the most-commonly used tools, they can have a learnability and discoverability deficit for users. Ensure that the arrow section of the button is visually signified, provide clear descriptive text labels, and do not use split buttons for navigation menus on websites.</p>
