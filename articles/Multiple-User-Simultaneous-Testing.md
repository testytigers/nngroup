<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>Testing 5-10 users at once lets you conduct large-scale usability testing and still meet your deadlines.

</div>

<div class="article-body">

<p>Sometimes you need to <strong> test a large number of users</strong>. One option, of course, is to apply the standard user-testing methodology, and just do more of it. Keep testing until you're blue in the face. Unfortunately, this often gets you into serious trouble with project deadlines.</p>

<p>Alternatively, you can use multiple-user simultaneous testing, or MUST (a term I have from Dennis Wixon). As the name indicates, with MUST, you test multiple users <strong>at the same time</strong> so you get done sooner. In most MUST studies, we <strong>test 5–10 users at once</strong> (but, as I describe below, you can also set up labs with many more test stations). Theoretically, there's no upper limit to the number of users you can test in each session.</p>

</div><h2 id="toc-when-to-use-must-1">When to Use MUST</h2>

<p>Most usability studies should be <a class="old" href="/articles/fast-cheap-and-good-methods/" title="Alertbox: Fast, Cheap, and Good - Yes, You Can Have It All"> simple and small-scale</a>, but in some scenarios, it's useful to conduct MUST:</p>

<ul>

<li>For <a href="https://www.nngroup.com/courses/measuring-ux/"><strong> quantitative studies </strong> and <strong> benchmarking</strong></a>, you typically need to <a class="old" href="/articles/quantitative-studies-how-many-users/" title="Alertbox: Quantitative Studies - How Many Users to Test?"> test at least 20 users per condition</a> in order to get statistical significance.</li>

<li>For <strong> long-duration tasks</strong>, you need to <strong> test each user for days or weeks </strong> to observe valid behaviors. Examples here include:

<ul>

<li><strong>Developer tools</strong>. You can't test a system to support professional programmers by having users develop and debug a 20-line "hello world" program; users must work through an industrial-scale problem. The same is true for other high-end problem-solving applications, such as CAD.</li>

<li><strong>E-learning</strong>. You can't test lesson 39 unless the learners have first made it through lessons 1–38. For a sufficiently advanced e-course, each test could take a week or more.</li>

</ul>

</li>

<li><strong>Usability focus groups</strong>. To alleviate the <a class="old" href="http://www.nngroup.com/articles/focus-groups/" title="The Use and Misuse of Focus Groups"> problems with traditional focus groups</a>, each participant should start with a one-on-one session testing the live user interface. Following the test sessions, participants can then congregate to discuss the experience and how it relates to their everyday needs. This method definitely requires MUST because all participants should test the interface just before the focus group meets.</li>

<li><strong>Games design</strong>. I describe this case in detail below.</li>

</ul>

<h2 id="toc-how-to-run-many-users-simultaneously-2">How to Run Many Users Simultaneously</h2>

<p>When testing many users, you usually need <strong> many test facilitators</strong>. The main exception is for the long-duration tests, where a few facilitators can circulate among users and/or review video recordings of critical incidents.</p>

<p>If you're one of the lucky few companies with many usability specialists, they can facilitate MUST sessions. This is expensive, but efficient: All you need to do is turn the experts loose, since they already know how to run a study.</p>

<p>Most companies, however, don't have enough usability pros to assign one to each test user. Happily, <a class="old" href="/articles/designers-developers-doing-usability/" title="Alertbox: Should Designers and Developers Do Usability?"> non-usability staff can run user test sessions</a>, especially if a seasoned usability expert has prepared the test plan and written the tasks.</p>

<p>For our latest MUST study, we hired cognitive science students from Don Norman's former department at the University of California, San Diego; they were excellent facilitators. In other studies, we've used developers and marketers from the project team. Being responsible for a MUST session is a great way for such team members to get intense exposure to customers.</p>

<h2 id="toc-training-facilitators-3">Training Facilitators</h2>

<p>Ideally, your new facilitators would go through a <a class="new" href="https://www.nngroup.com/courses/usability-testing/" title="Nielsen Norman Group: 'Learning-by-Doing: User Testing,' a 3-day hands-on event for a team where we test its own design as the main exercise"> full usability training workshop</a>, but this is rarely possible in practice. Still, it's best if you spend at least a few hours training facilitators before giving them a go with real users:</p>

<ul>

<li>First, of course, you should explain the <strong> theory and best practices of user testing</strong>, including steps such as "keep quiet and let users do the talking," which I've discussed many times before.</li>

<li>Second, newbie facilitators should <strong> watch an experienced usability expert </strong> run a sample session with a pilot user. Doing so

<ul>

<li>shows newbies how to facilitate a study, and</li>

<li>better concretizes the test plan and test tasks than simply discussing them or going through them on paper.</li>

</ul>

</li>

<li>Third, conduct a <strong> role-playing exercise </strong> in which the usability expert plays the user and simulates difficult situations that facilitators can encounter, such as users who don't talk or users who ask if they can use certain features. (In the latter case, we typically say: <em> "You can do anything you would normally do at home/in the office."</em>)</li>

</ul>

<h2 id="toc-preparing-the-users-4">Preparing the Users</h2>

<p>There's <strong> very little special preparation </strong> to do for MUST study participants. Just follow standard procedure for <a class="old" href="/articles/recruiting-test-participants-for-usability-studies/" title="Alertbox: Recruiting Test Participants for Usability Studies"> recruiting test users</a>, welcome them to the session, give them consent forms and instructions, and so on.</p>

<p>However, the actual MUST sessions differ from traditional sessions in two key ways:</p>

<ul>

<li><strong>Thinking aloud </strong> doesn't work when people are tightly packed into small cubicles, so you shouldn't include the usual instruction for users to vocalize their thoughts as they move through your design.</li>

<li>You can <strong> minimize the distraction </strong> of having multiple users by telling participants that they'll likely be working on different tasks. This reduces their natural inclination to look at other users' screens and also prevents people from feeling stupid if other people finish before them and leave the room.</li>

</ul>

<h2 id="toc-why-not-use-automated-testing-5">Why Not Use Automated Testing?</h2>

<p>Why is MUST worth the trouble when you can just outsource your testing to one of several services that promise to run a <strong> panel of users </strong> through your site and give you elaborate charts of the outcome? Because usability is strategically vital to the success of any website or interactive product — and outsourced panels just aren't up to the job.</p>

<p>The #1 rule of all user testing is to test with <strong> representative customers</strong>. Panels rarely meet this requirement; they're composed of <strong> people who get paid a pittance to sit like drones </strong> and complete online tests. If you're targeting a very low-level audience, then this might be worth a gamble. But not if you're a <a class="old" href="/articles/b2b-usability/" title="Alertbox: Business-to-Business Usability"> B2B site</a> selling to construction engineers or hospital pharmacists. Not even if you're a normal B2C e-commerce site.</p>

<p>For fun, some of my colleagues once signed up with a panel operator. Despite being fully truthful in their responses to the initial questionnaire (which many people aren't when they register for panels), they were assigned to several studies for which they were not even remotely in the target audience. These "studies" are often a form of <a class="old" href="/articles/voodoo-usability/" title="Alertbox"> voodoo usability</a> that generate misleading results.</p>

<p>Even if a panel operator could get you representative customers, automated studies are still a shadow of real usability research because you can't sit next to the user. <strong> Direct observation </strong> is invaluable, both for <strong> seeing the details </strong> that would never get reported in a chart, and for gaining the <strong> deep understanding </strong> of each user's individual behavior.</p>

<p>Based on user responses to questions, a screener assigns users to various segments. It's common to find that such assignments are a bad fit, however. Using typical <a href="https://www.nngroup.com/courses/personas/"><span class="new"> persona</span></a> names, for example, you might say, <em> "no way is this user a Susan, but he's a pretty close Patrick," </em> and then reclassify the user. Other times, you might have to throw out the data because someone is simply not in your target audience; still other times, you can use that person's insights qualitatively — as a representative of a corner case — even though you won't include them in the core sample. When you're in the room with users, you can identify these situations and act accordingly. When all you get is a chart, you won't even know that some of the test participants were border cases or outside your audience entirely.</p>

<p>Finally, having members of your project team serve as facilitators and get live exposure to real customers is immensely motivating. A chart from 500 anonymous panel members doesn't have a fraction of the <strong> emotional impact </strong> of sitting next to a few fellow human beings as they suffer through your design.</p>

<h2 id="toc-high-end-must-lab-microsoft-games-studios-6">High-End MUST Lab: Microsoft Games Studios</h2>

<p>There are many different ways to run MUST. The most impressive setup I know of is at Microsoft Games Studios. Here's one of its playtest labs:</p>

<p style="width: 600px; margin-left: auto; margin-right: auto; "><img alt="Photo of a row of test cubicles with game players at Microsoft Games Studios" height="360px" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/microsoft-playtest-lab.jpg" width="600px"/> <em> Playtest lab at Microsoft Games Studios.<br/>

Headsets are helpful when many people in the same room are playing audio-intensive games. </em></p>

<p style="width: 600px; margin-left: auto; margin-right: auto; "><img alt="Plan of test lab configuration, showing rows of cubicles in each lab" height="400px" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/microsoft-games-studios-labs.gif" width="600px"/> <em> Floor plan for three labs at Microsoft Games Studios. </em></p>

<p>According to Dennis Wixon, Microsoft Games Studios' User Research Manager, his group runs 8,000 gamers through its labs every year. This is a huge amount of user testing — far beyond the amount of research conducted by the average company. No wonder Microsoft needs a high-end lab devoted exclusively to gameplay testing.</p>

<p>(Microsoft tests its software and websites in other usability labs. These labs don't have Xbox 360s at each seat as they might distract users from making their pie charts in Excel. :-)</p>

<p>Why does Microsoft do so much usability testing for its games? A <em> huge </em> amount of money is at stake. A game like <cite> Halo 3 </cite> is considered the "drive title" for the Xbox 360. If <cite> Halo 3 </cite> is great, gamers will buy the 360. If <cite> Halo 3 </cite> sucks, they'll stay with their old Xbox or get a PlayStation.</p>

<p>I don't know the budget for Wixon's group, but I'd bet it's a tiny fraction of the $300M <cite> Halo 3 </cite> sold in its first week alone — and an even tinier fraction of those Xbox sales that are dependent on the title's success. Obviously, the usability group works on many other games besides the Halo series, but for the latest version of that game alone, they <a class="out" href="http://www.wired.com/gaming/virtualworlds/magazine/15-09/ff_halo " title=" WIRED Magazine: Halo 3, How Microsoft Labs Invented a New Science of Play"> analyzed more than 3,000 hours of gameplay across 600 test participants</a>. This detailed user research made <cite> Halo 3 </cite> much more fun to play and also more approachable for new players, who are essential to boosting sales beyond those of <cite> Halo 2 </cite> .</p>

<p>The second reason to test multiple users for computer games is that it's a more <strong> difficult field of user interface design </strong> than the domains we usually test. Every game is a new world, whereas all websites follow much the same rules.</p>

<p>When we test websites, we can rely on <a class="new" href="/reports/" title="Nielsen Norman Group: list of research reports on Web usability"> thousands of documented guidelines</a> that explain user behavior with this style of interaction design. So, when we observe a behavior, we can typically conclude: <em> "oh, this is an instance of guideline #728," </em> which we have already seen hundreds of times with other users on other sites. Recognizing a documented behavior means that we don't need to test that many users, because a few observations suffice to build confidence that we're on the right track. Also, data analysis is simplified because we can build on published research.</p>

<p><a href="https://www.nngroup.com/articles/game-user-research/">Games require a more delicately balanced user experience</a><strong> </strong> than functional interfaces. Say that you're designing a weapon's targeting system. If you work for the Army, you want to make the system's user interface as fast and accurate as possible. Shooting the bad guys before they get you is obviously the way to go. But, if you're doing the equivalent design for <cite> Halo 3</cite>, the answer isn't as obvious. Make targeting <em> too </em> fast and easy, and the game soon stops presenting a challenge. Sure, you could blast all the bad guys without breaking a sweat, but the game's <em> purpose </em> is to make you feel like you're on the edge and living dangerously. (A danger real soldiers typically want to avoid.)</p>

<p>It's easy to test a UI to eliminate difficulties. It's hard to determine whether one presents just the right amount of difficulty. That's why Microsoft Games Studios runs so many users through its playtest labs.</p>

<h2 id="toc-simpler-must-labs-7">Simpler MUST Labs</h2>

<p>You can run MUST studies without the fancy lab. The following photo shows a study we ran recently, where we tested 5 users in each session.</p>

<p style="width: 600px; margin-left: auto; margin-right: auto; "><img alt="Photo of several test cubicles set up within a bigger lab" height="250px" loading="lazy" src="//media.nngroup.com/media/editor/alertbox/multiple-user-simultaneous-testing.jpg" width="600px"/> <em> Impromptu cubicles installed in a meeting room for multiple-user simultaneous testing.<br/>

(The photo shows 3 of the lab's 5 test stations.) </em></p>

<p>In our lab, we simulated cubicles by taping <strong> cardboard partitions </strong> to each desk. Of course, it's better to use real cubes, but our discount cubes worked swimmingly. We used <strong> slave monitors in each cubicle </strong> so facilitators could get a good view of the action on their user's screen without having to lean in. However, for most studies, it's perfectly fine to use a single monitor.</p>

<p>In addition to cubicles, we've used three other setups for previous MUST studies:</p>

<ul>

<li><strong>Single-person offices </strong> for each user. (For an intranet study, we used participants' actual offices.) Individual offices can be in different parts of the building (or even in different buildings) so long as each user is assigned a facilitator who stays for the session's duration.</li>

<li><strong>Large-scale usability labs </strong> with a row of test labs. In such cases, we tested each user in a separate lab. This setup is particularly suited for studies in which users work on large-scale problems for days at a time, and a few facilitators move around among users. Because the facilitators can enter and leave each lab's observation room without the user's knowledge, it's possible to watch many users in a day without disrupting their concentration. Also, you can leave users who are working on a part of the task you don't care about without communicating this fact and thereby biasing their behavior.</li>

<li><strong>Offices turned into a networked lab</strong>. This case mixes the previous two setups: many single-user offices are wired to a single observation room. You can do all this over the local-area network, which can carry the streaming screendumps for a remote slave monitor as well as webcam views of the users.</li>

</ul>

<p>Ultimately, the vast <strong> majority of usability studies should be qualitative </strong> and <a class="old" href="/articles/why-you-only-need-to-test-with-5-users/" title="Alertbox: Why You Only Need to Test With 5 Users"> test 5 users</a>. Still, there are situations in which you need more, and that's when it's nice to have MUST in your toolkit so that you can get the study done before your deadline.</p>

<p>Learn the many different variants of user testing (and when to do what) in our full-day <a href="https://www.nngroup.com/courses/usability-testing/">Usability Testing course</a>.</p>
