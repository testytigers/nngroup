<span class="article-summary-label">

Summary:&nbsp;

</span>Applications can give users access to a richer feature set by using the same few commands to achieve many related functions.

</div>

<div class="article-body">

<p>In application design, there's a tension between <strong> power </strong> and <strong> simplicity</strong>: Users want the ability to get a lot done, but they don't want to take the time to learn lots of complicated features.</p>

<ul>

<li>One way to address this dilemma is to use <a class="old" href="/articles/progressive-disclosure" title="Alertbox"> progressive disclosure</a> — that is, to show users only the most important options until they ask for the advanced features.</li>

<li>Another good approach is to use <strong> generic commands</strong>, which <strong> remain the same across many different contexts </strong> and thus reduce complexity.</li>

</ul>

</div><h2 id="toc-cut-copy-paste-1">Cut, Copy, Paste</h2>

<p>The <strong> <em> cut-copy-paste </em> </strong> triad offers the most famous example of generic commands. These 3 basic commands suffice to let users do everything from move text to edit movies. In fact, because they work across so many applications, I view them as " <strong> super-generic commands</strong>."</p>

<p>The first guidelines for generic commands are:</p>

<ul>

<li>If at all applicable to your domain, your application should support the super-generic commands that people expect and know from other applications.</li>

<li>In particular, provide <em> cut-copy-paste </em> commands for moving stuff around.</li>

</ul>

<p>One of the big criticisms of iPhone version 1.0's user experience is that it doesn't support <em> cut-copy-paste</em>, even though users definitely expect these commands in any modern design.</p>

<p>The <em> cut-copy-paste </em> triad wasn't the original generic editing command set. The <a class="out" href="http://www.digibarn.com/friends/curbow/star/retrospect/" title="The Xerox 'Star': A Retrospective, paper by Jeff Johnson and colleagues"> original designers at Xerox PARC</a> used <em> move-copy-delete</em>. If you think about it, these two triads both map to all common user actions, they just do it in different ways:</p>

<p>From the above table, it might seem that <em> move-copy-delete </em> is the superior set of generic commands. In practice, however, it forces you to specify <em> where </em> you're copying or moving to and from. Having 2 arguments per command complicates matters. In contrast, <em> cut-copy-paste </em> employs an intermediate state: the clipboard, which is a different complication but allows each command to proceed with only 1 argument.</p>

<p>It's hard to say which of the two models is superior. But it's clearly best to <strong> pick one </strong> model and stick to it everywhere. Much confusion would ensue if people had to use one model half the time and another model the other half of the time.</p>

<h2 id="toc-benefits-of-generic-commands-2">Benefits of Generic Commands</h2>

<p>Generic commands have three advantages:</p>

<ul>

<li>They are <strong> ubiquitous</strong>, so users will <strong> expect </strong> to find them (and will <strong> look </strong> for the commands without being prompted to do so).</li>

<li>They are <strong> consistent</strong>, so users will know how to <strong> use </strong> them.</li>

<li>They <strong> replace </strong> many commands that are more specialized, so users have less to <strong> learn</strong>.</li>

</ul>

<p>If users are to form expectations about available commands, consistency is essential. Consistency is further enhanced when commands are always assigned the same <strong> command-key </strong> shortcuts. Thus, rather than looking for a command, users can, for example, simply type <em> Ctrl-C </em> when they want to copy something.</p>

<p>Consistency doesn't require that generic commands work identically across different contexts — just that users <em> perceive </em> that they do so. For example: cutting a piece of an image using a graphics editor typically leaves a blank area on the canvas, while cutting words using a word processor closes up the remaining text without leaving a gap.</p>

<p>You could expose these different operations by using separate user interface commands — such as <em> cut picture </em> and <em> cut word</em>s — but doing so would add unnecessary complexity. Yes, when users issue a <em> cut </em> command in the two contexts, different subroutines execute, but it's better to hide this difference and create the <strong> user illusion </strong> that a single command performs these similar operations.</p>

<p>On the Web, a simple example of a generic website command is "go to the homepage." Often, sites support this command using a logo in the page's upper left corner that links to the homepage. Unfortunately, not all sites do this, which seriously reduces usability for the Web as a whole.</p>

<p>Currently, the only generic Web commands that truly work are those in browsers rather than on individual sites. Examples include <em> Back</em>, <em> Forward</em>, and <em> Print</em>. In the latter case, it would be much more useful if the generic <em> Print </em> button subsumed a page's <em> Printer-friendly version </em> feature; clicking <em> Print </em> should print a printer-friendly view, not the view on the screen. You can implement this improved user interface by providing two CSS style sheets for the page: one for displaying on the screen and one for printing.</p>

<h2 id="toc-ipod-touch-examples-of-generic-commands-3">iPod Touch: Examples of Generic Commands</h2>

<p>Generic commands don't have to be issued through menus and command-key shortcuts. As the following screenshots show, the iPod Touch — a touch-screen tablet device that's basically an iPhone, minus the crappy phone service — uses gestures and icons instead:</p>

<p style="text-align:center;"><img alt="iOS screenshots from 2007" height="510" loading="lazy" src="//s3.amazonaws.com/media.nngroup.com/media/editor/2014/10/28/ipod-touch-screenshots.jpg" width="920"/><br/>

<em>Three iPod Touch applications, shown in both vertical and horizontal tablet orientations.<br/>

Left to right: photo viewer, music player, and Web browser.</em></p>

<p><strong>Turning</strong> the device is a generic command that alternates vertical and horizontal display modes. In the photo viewer, when users turn the tablet in the same direction as the photo's orientation, it makes the image larger. In the music player, turning doesn't make the record covers larger (since they're square), but rather lets users scroll through albums. In the Web browser, alternating between vertical and horizontal provides different Web page views, both of which are useful.</p>

<p>The point? One operation — turning — has multiple effects that are recognizably similar, but differ in their specifics depending on the individual application's demands.</p>

<p>The device also provides generic commands in the form of <strong>VCR-style icons</strong>: a right-pointing triangle means "play" (or "forward"), a left-pointing triangle means "rewind" (or "go back"), and a double triangle means "do it faster" than a single triangle.</p>

<p>VCR icons have achieved the status of super-generic commands, and it's highly recommended that you use them if your application has player-style functionality.</p>

<p>Unfortunately, the iPod user experience is degraded by <strong>poor attention to detail</strong> in the generic-command design. For example, in the photo player, the player buttons don't move as you turn the tablet, making the "play" button look like an upward-pointing triangle in the horizontal orientation. In the music player, horizontal orientation removes most of the buttons and changes the play button's appearance (putting it inside a circle). Of the three applications, only the Web browser treats the play commands correctly when you turn the tablet.</p>

<p>Generic commands give users increased power without increasing user-experience complexity. But, to be truly generic, such commands must be available everywhere in your user interface.</p>
