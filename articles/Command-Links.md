<div class="article-summary article-heading-small-light">

<span class="article-summary-label">

Summary:&nbsp;

</span>Application commands can be presented as buttons or as links, which offer more room for explanation. For primary commands, however, buttons are still best.

</div>

<div class="article-body">

<p>In simpler times, there was one set of <a class="new" href="/courses/web-ux-design-guidelines/" title="Nielsen Norman Group: full-day training class, Fundamental Guidelines for Web Usability"> guidelines for websites</a> and another set of <a class="new" href="/courses/topic/applications/" title="Nielsen Norman Group: full-day training class, Application Usability 1 - Page-Level Building Blocks for Feature Design"> guidelines for applications</a>. And the two were clearly <em> different</em>. For example, there were different rules for presenting the user's options:</p>

<ul>

<li><strong>Websites </strong> offered <strong> navigation </strong> through <strong> links </strong> (<a class="old" href="/articles/guidelines-for-visualizing-links/" title="Alertbox: Guidelines for Visualizing Links">underlined colored text</a>).</li>

<li><strong>Applications </strong> offered <strong> actions </strong> through <strong> menus </strong> and <strong> buttons</strong>.</li>

</ul>

<p>The guidelines for websites and applications were different (and continue to be different) because of one of usability's foundational tenets: Good design is based on (a) the users and (b) their tasks. Websites and applications differ fundamentally along the latter dimension:</p>

<ul>

<li><strong>Websites</strong>: The user's primary task is to <strong> move around </strong> an information space and <strong> read </strong> its content.</li>

<li><strong>Applications</strong>: The user's primary task is to <strong> change the state </strong> of some data set by issuing <strong> commands</strong>.</li>

</ul>

<p>In fact, the very <strong> definition of an application </strong> is that its features <strong> affect something external </strong> to its own user interface. Using an application will make something change, because a user asks for it to be changed. In contrast, a website doesn't change simply because it's being used; the pages are always the same. (Although the information might change, website pages are <em> conceptually </em> static. For example, a page with tomorrow's weather forecast always contains this information, even though one day it displays the icon for rainy weather and another it shows the icon for sunshine.)</p>

</div><h2 id="toc-blurring-the-line-between-apps-and-sites-1">Blurring the Line between Apps and Sites</h2>

<p>Over the last decade, the clear distinction between websites and applications has blurred.</p>

<p>First, on the <strong> semantic level</strong>, websites are offering more and more features. The first widely used feature was "add to shopping cart," and it's always been a <a class="old" href="/reports/ecommerce-user-experience/" title="Nielsen Norman Group report: Design Guidelines for E-Commerce User Experience"> guideline for e-commerce usability</a> to show this feature as a button, even though it's found on a website.</p>

<p>So, for application-like website components -- those representing features or commands, rather than plain information -- you should follow the guidelines for application usability (as with the "add to shopping cart" feature).</p>

<p>The second issue is harder to deal with: On the <strong> syntax level</strong>, the distinction between buttons and links has blurred, because <strong> some commands are being shown as links</strong>.</p>

<p>Fortunately, we have at least one clear rule: <strong> don't use buttons for navigation</strong>. Users should click a plain link to move to another page of information.</p>

<p>Even this rule has an exception, however: the "continue shopping" and "proceed to checkout" options in a shopping cart are traditionally shown as buttons, even though they're pure navigation. Nothing changes when users click one of these two options -- they simply move to another page that has the commands they need to use. But because checkout is part of a workflow process, it gets a waiver from the plain-link navigation rule.</p>

<p>Mainly, though, the rule is to <strong> use links when users move between pages</strong>. Among many other benefits, plain links let users open a new page in a new tab or window if they so desire, and you can also <a class="old" href="/articles/change-the-color-of-visited-links" title="Alertbox: Change the Color of Visited Links"> show link text in different colors</a>, depending on whether the user has visited the destination before.</p>

<h2 id="toc-guidelines-for-command-link-design-2">Guidelines for Command Link Design</h2>

<p>Windows Vista introduced a new GUI widget for commands: the <strong> command link</strong>. Once something is in the system that people use on a daily basis, it becomes a de facto standard. Because they'll encounter them frequently in Vista, users will come to <strong> know and expect command links</strong>.</p>

<p>Many websites already use links for commands. Still, while users are increasingly aware that links can activate a command, there's still the risk of confusing users because most links are navigational.</p>

<p>To reduce confusion, link text should <strong> explicitly state that it leads to an action </strong> and not just to a new page. It's not enough to communicate this info in the surrounding text; users often <a class="old" href="/articles/how-users-read-on-the-web/" title="Alertbox: How Users Read on the Web"> scan Web pages</a> for the areas they can act on. Thus, you should assume that most users will only read the link text. In fact, users often read only the link text's first few words, so it's important to <strong> start with a word </strong> (typically a verb) that <strong> indicates the action </strong> that results if they click the link.</p>

<p>As for <strong> capitalization rules</strong>, refer to the guidelines for regular links in your corporate style guide. If you don't have a style guide, use sentence-style capitalization (that is, capitalize only the first letter of the first word in the command name). The exception would be if it's an inline link within a surrounding sentence. However, it's typically best to avoid having commands in the body text; inline linking should be limited to navigation.</p>

<p><strong>Limit the use of command links </strong> to:</p>

<ul>

<li><strong>Actions with minor consequences</strong>, since users might click something that looks like a link with the expectation that all it'll do is bring up a new page. In a brokerage application, for example, continue to use a button for the "buy this stock" command.</li>

<li><strong>Secondary commands</strong>, since users will scan the screen for a button when they're looking for the "serious" or main commands. Thus, you should display the commands that are most important -- whether from the user's perspective or your own -- as buttons. For example, continue to use a button for "add to shopping cart."</li>

</ul>

<p>Despite these limitations, command links have their place because they introduce some benefits. Most notably, with a link, you can write a <strong> longer command name </strong> and thus make it more descriptive, whereas button labels have to be short (4 words or less) or the button will look weird. Of course, since users don't like to read, you should keep your command descriptions as short as possible.</p>

<p>Vista showcases another benefit of command links: the ability to <strong> add explanatory text </strong> below the primary link text. You can present this explanation in a smaller typeface to emphasize its secondary nature (so experienced users won't waste time reading it). Because buttons are enclosed and thus self-contained, it's harder to add an explanation next to a command button. And, if you do, users are likely to overlook it.</p>

<p>The time has come to show some of your commands as links. Just don't overdo it.</p>
